# Precision lyric synchronization vNext design

## Purpose

This design upgrades the Tanisea lyric film from phrase-level timing with proportional within-line subdivision to evidence-backed Russian word and semantic-group alignment. It also simplifies the upper frame, gives the bottom spectrum materially more visual reach, establishes release-blocking audiovisual QA, and publishes the result with neutral technical documentation.

The public deliverable remains a 1080×1080, 60 fps lyric film. Timing data is stored against the locked 44.1 kHz soundtrack as integer sample indices. A separate 120 fps proof exposes timing state for verification without adding diagnostic clutter to the public master.

## Success criteria

The work is complete only when all of the following are true:

1. The exact soundtrack remains locked to SHA-256 `93084f293d491da1519732f3fa3cf6416c783d04e8ca18b5569c7608a8d4540d`, 44.1 kHz stereo, and 153.000 seconds.
2. No production word or semantic boundary is generated by dividing a line duration into percentages.
3. Every performed Russian token in the 24 displayed lines has a sample-indexed interval, evidence, confidence, and uncertainty, or an explicit documented exclusion.
4. Both repeated chorus performances are aligned independently. They may share semantic structure but never copied absolute or normalized timing.
5. English segment positions remain fixed while chronological Russian cues may target them forwards, backwards, repeatedly, simultaneously, or not at all when an exclusion is documented.
6. At least two genuine backward transitions are present and reviewed: the meaning order in `V1-03` and `V1-08`.
7. Every 60 fps cue is mapped to the nearest frame with absolute quantization error at or below 8.334 ms; every 120 fps proof cue is at or below 4.167 ms.
8. The top reactive rail and top-right RMS/peak/FPS block are absent from the public composition.
9. The bottom 64-band spectrum has at least 96 px of measured core travel and up to 18 px of separately styled, documented transient extension without entering the lyric safe area.
10. Automated timing, semantic, visual-state, determinism, decode, metadata, audio-identity, and checksum gates all pass twice from a clean install.
11. The final GitHub project, including its release assets, includes a lossless 2160×2160 hero PNG, production master, 120 fps synchronization proof, machine-readable alignment data, technical audit, checksums, and a neutral professional README.

## Approaches considered

### Manual frame nudging

Manual frame nudging is useful for perceptual review but cannot be the timing authority. It is limited by display cadence, is difficult to reproduce, and does not explain uncertainty.

### ASR-only alignment

ASR-only word timestamps are unsuitable for processed singing. Transcription and alignment errors can look plausible while being hundreds of milliseconds wrong. ASR remains useful as independent evidence, not as the source of truth.

### Hybrid alignment — selected

The selected architecture combines a latency-checked vocal stem, a verified Russian transcript, Russian Montreal Forced Aligner output, WhisperX alignment as an independent comparison, waveform and spectrogram evidence, and manual adjudication of disagreements. Final boundaries are stored as source-audio sample indices with explicit uncertainty. This is slower, but it is reproducible and makes every claim auditable.

## Audio and alignment architecture

### Locked audio authority

The checked-in `public/soundtrack.m4a` remains the sole time authority. The pipeline decodes it once to stereo 44.1 kHz PCM without resampling. All derived stems and analysis files must retain exactly 6,747,584 decoded samples per channel or record and compensate a measured latency relative to that source.

A sample index is the canonical timestamp. Milliseconds are presentation values only:

```text
seconds = sampleIndex / 44100
milliseconds = sampleIndex × 1000 / 44100
```

At 44.1 kHz, one sample is approximately 22.676 microseconds. This is storage resolution, not a claim that a sung phoneme has zero perceptual ambiguity.

### Vocal evidence

Demucs generates a vocal stem for alignment. The pipeline measures stem latency against the source mix using cross-correlation around clear vocal attacks and stores the compensation in the alignment manifest. A stem whose latency is inconsistent across the track or whose decoded length differs from the locked source fails preparation.

The accompaniment-free stem improves phoneme visibility, but boundaries are always checked against the original mix so separation artifacts cannot become the authority.

### Independent alignment paths

Each of the 24 authoritative Russian lines is segmented with conservative line windows derived from the existing audits. The same verified transcript is processed through:

- Russian MFA acoustic and pronunciation models;
- WhisperX forced alignment using the supplied transcript rather than unconstrained transcription;
- a waveform/onset trace from the latency-corrected vocal stem;
- a spectrogram view of the original mix and vocal stem.

The pipeline retains every raw result. It never silently interpolates an unaligned word.

### Boundary adjudication

For every token boundary, the manifest stores:

```ts
type AlignmentEvidence = Readonly<{
  method: 'mfa' | 'whisperx' | 'waveform' | 'spectrogram' | 'manual-review';
  sampleIndex: number;
  note: string;
}>;

type SourceToken = Readonly<{
  id: string;
  text: string;
  startSample: number;
  endSample: number;
  confidence: 'high' | 'medium' | 'low';
  uncertaintySamples: number;
  evidence: readonly AlignmentEvidence[];
}>;
```

Clear boundaries may pass automatically only when independent methods agree within 25 ms after latency compensation. Processed or reverberant boundaries may use up to 50 ms uncertainty, but require a manual-review evidence record. A boundary with more than 50 ms unresolved spread blocks release.

The selected timestamp is the reviewed boundary, not an arithmetic midpoint chosen merely to reduce spread. The audit records why that boundary best represents the first meaningful performed phoneme or the end of the last meaningful phoneme.

### Frame mapping

The public renderer maps each sample-indexed event to the nearest 60 fps frame:

```text
frame = round(sampleIndex × fps / 44100)
errorMs = (frame / fps - sampleIndex / 44100) × 1000
```

The 60 fps absolute error must not exceed 8.334 ms. The 120 fps proof uses the same data and must not exceed 4.167 ms. Reports list the exact error for every event rather than claiming a one-millisecond visual refresh.

## Semantic mapping

### Data model

Russian source tokens and English display segments are separate structures. Cue events are chronological and reference both:

```ts
type SemanticCue = Readonly<{
  id: string;
  startSample: number;
  endSample: number;
  sourceTokenIds: readonly string[];
  targets: readonly string[];
  activation: 'forward' | 'backward' | 'repeat' | 'simultaneous' | 'hold';
  confidence: 'high' | 'medium' | 'low';
  uncertaintySamples: number;
  mappingNote: string;
}>;
```

Every target must reference a stable English segment ID in the same line. Source tokens may be grouped into one semantic cue, and one cue may target several English segments. Clear performed meaning may not be left unmapped.

### Required non-linear sequences

`V1-03` keeps the natural English display order while following the Russian performance: the cue for `гложут` targets “gnaw at me,” followed by `вопросы` targeting the earlier “questions” segment. The visible focus therefore moves right, then backward left.

`V1-08` begins with `кто` targeting “someone,” followed by `за спиною` targeting the earlier “Behind my back” segment, then moves forward to “couldn't hold back” and “a laugh.”

The complete line remains stationary. Backward movement is a focus change, never a reversible fill or text rearrangement.

### Focus interaction

On the nearest cue frame, a crisp underline/contact mark appears immediately on every active target. Weight, luminance, and glow reach their full state over the next two 60 fps frames. The outgoing target releases over two frames. This preserves exact contact while preventing a backward jump from looking like a glitch.

Inactive text remains readable. The independent line-duration bar may continue monotonically; it never controls semantic focus.

Per-character emphasis is not required. It may be added only when a reviewed stressed syllable clearly benefits from it, remains typographically stable, and does not imply unsupported phoneme precision.

## Visual composition

### Upper frame cleanup

The global `AudioMotionLine` currently placed near the top of every frame is removed. The top-right RMS, peak, and FPS telemetry is removed from the public `FrameChrome`. The top-left artist/remix identity and restrained outer frame remain.

Scientific values belong in the proof and audit artifacts, not in the public artwork. This keeps the upper negative space clean and prevents the composition from resembling a diagnostic dashboard.

### Bottom spectrum

The spectrum remains 64 logarithmic bands across the existing 960 px width. The rail grows from a 70 px container with approximately 34 px of useful bar height to a container of approximately 150 px with:

- at least 96 px of measured core travel;
- a two-output-pixel minimum core for active bands;
- a separate 0–18 px transient extension/cap driven by the documented impact envelope;
- frequency ticks below the baseline;
- no top heading competing with lyric text;
- a hard top boundary below the lyric safe area.

Measured core height is derived only from the frozen band value and published display transform. Transient extension uses a distinct lighter cap so artistic impact never masquerades as additional measured magnitude.

Verse/build lyric layout retains at least a 36 px gap above the maximum visualizer extent. Chorus layout is checked at the highest transient frame. Any collision is release-blocking.

### Hero image

The repository hero is rendered directly from the final source at 2× scale as a 2160×2160 lossless PNG. It must show the cleaned upper frame, the expanded visualizer, sharp typography, and a representative active semantic focus. JPEG intermediates are prohibited.

## Source structure

The current `LyricFilm.tsx` mixes rendering primitives, semantic focus, chrome, and spectrum logic. The change introduces focused modules without unrelated refactoring:

```text
projects/tanisea-lyric-film/
  src/
    timing/
      alignment-types.ts       sample-indexed contracts
      tanisea-alignment.ts     reviewed production alignment data
      validate-alignment.ts    runtime contract and frame-bound checks
    components/
      LyricDisplay.tsx         stationary segments and semantic focus
      SpectrumRail.tsx         measured core plus artistic impact cap
      FrameChrome.tsx          simplified public frame
    focus-state.ts             deterministic cue-to-style calculation
    LyricFilm.tsx              composition orchestration
  scripts/
    prepare-alignment.ts       source/stem identity and latency checks
    verify-alignment.ts        manifest, evidence, and quantization audit
    render-sync-proof.ts       120 fps diagnostic proof orchestration
    verify-render.ts           decoded delivery and visual-state audit
  tests/
    alignment.test.ts
    focus-state.test.ts
    spectrum-geometry.test.ts
    render-contract.test.ts
```

The reviewed alignment JSON and technical report live under `audits/`. Generated stems, PCM files, model caches, and temporary frames remain ignored and are never committed.

## Error handling

Alignment preparation fails on soundtrack checksum mismatch, decode geometry mismatch, uncorrected stem latency, missing transcript tokens, unknown dictionary words without an explicit pronunciation, or missing raw evidence.

Runtime validation fails on non-integer sample indices, reversed or overlapping token intervals, cue events outside a vocal window, unknown source or target IDs, undocumented low-confidence cues, missing backward sequences, or frame errors beyond the cadence bound.

Rendering fails when fonts or feature artifacts do not load. Delivery verification fails on codec, dimensions, cadence, frame count, colour metadata, decode errors, audio packet identity, checksum mismatch, safe-area collision, or nondeterministic selected-frame hashes.

No script converts a failure into a warning during release mode.

## QA architecture

### Test-first gates

Every behavior change begins with a failing automated test. The suite covers:

- exact soundtrack identity and sample geometry;
- complete token and semantic mapping coverage;
- independent repeated-chorus timing;
- chronological cues with non-monotonic target positions allowed;
- the required `V1-03` and `V1-08` backward sequences;
- repeated and simultaneous targets;
- nearest-frame quantization bounds at 60 and 120 fps;
- immediate contact-mark activation and bounded two-frame style easing;
- spectrum core/cap separation, maximum height, symmetry, and safe area;
- absence of public top telemetry and the global upper rail;
- deterministic state and selected-frame hashes.

### Alignment evidence review

The verifier emits a table for every token and cue containing source samples, milliseconds, MFA and WhisperX candidates, selected boundary, spread, confidence, uncertainty, 60 fps frame/error, and 120 fps frame/error.

Every boundary over 25 ms method spread enters a mandatory review queue. Manual adjudication records a selected boundary and marks the item resolved; no unresolved item may remain at release.

### Audiovisual review artifacts

The pipeline renders:

- a normal-speed clip around every line handoff;
- half-speed copies with pitch preserved;
- dedicated clips for every backward, repeated, and simultaneous cue;
- a 120 fps proof with Russian token, English target, sample index, confidence, uncertainty, and frame error;
- dense contact sheets around the two backward sequences and the final lyric-to-outro handoff.

The public master contains none of those diagnostics.

### Repeated verification

Release requires two clean verification runs after `npm ci`. Each run performs typechecking, unit tests, composition discovery, alignment validation, selected-frame rendering, full master decode, frame counting, metadata inspection, audio packet hashing, artifact hashing, and requirement-matrix generation.

Selected source frames are rendered twice and must produce identical hashes. The final encoded master is decoded completely twice. The copied archival AAC packet stream must match the locked source packet hash.

## Delivery and publication

### Public artifacts

The release contains:

- the verified 1080×1080 60 fps production master;
- a compact platform-safe derivative only if it is clearly named and audited separately;
- the 120 fps synchronization proof;
- the 2160×2160 lossless hero PNG;
- source archive and lockfile;
- alignment manifest, technical timing report, final QA report, and SHA-256 checksums.

Large media belongs in the GitHub release rather than Git history. Source, manifests, reports, and the hero PNG are committed normally.

### Neutral README and notes

The README describes the artifact, reproducibility, synchronization model, measurable guarantees, build commands, deliverables, and rights. It does not expose prompt history, internal agent/tool names, local paths, conversational approvals, speculative scoring, or who supplied individual decisions.

Public synchronization language is precise: “sample-indexed alignment with frame-bounded rendering.” It does not claim literal one-millisecond visual refresh or zero-uncertainty phoneme perception.

Historical reports may remain for provenance, but the README links primarily to the final alignment and QA reports. New reports use neutral engineering language and avoid reconstructing the private working process.

## Completion audit

Before publication, the final QA report maps every success criterion in this design to authoritative evidence: source files, manifest fields, test names, command output, rendered artifacts, decoded media properties, hashes, and release URLs. Missing or indirect evidence is a failure, not a pass.

The work is not complete until the repository and GitHub release both contain the verified final state and a fresh clone can reproduce all non-proprietary validation steps from the committed lockfile.
